# Meter Reader — распознавание счётчиков по фото

HTTP-сервис на Python (FastAPI). Принимает фото счётчика и возвращает тип счётчика, показание (расход), производителя, модель и серийный номер.
Распознаёт мультимодальная модель **Qwen3.6-35B-A3B** в Yandex Cloud AI Studio (внешний сервис, через OpenAI-совместимый API).

Сейчас проверено распознавание **счётчиков воды** (горячей и холодной). Электричество, газ и тепло описаны в промпте, но на датасетах ещё не проверялись.

Это часть репозитория бота ЖКХ в MAX: бот ходит сюда по `RECOGNIZER_URL`, клиент — `app/integrations/recognizer.py`
(см. «Как бот использует ответ» ниже). Сервис можно запускать и отлаживать отдельно, бот для этого не нужен.

## Запуск вместе с ботом (из корня репозитория)

В корневом `.env`: `COMPOSE_PROFILES=recognizer`, `YC_API_KEY`, `YC_FOLDER_ID`,
`RECOGNIZER_URL=http://meter-reader:8000/recognize`. Затем `docker compose up -d --build`;
логи — `docker compose logs -f meter-reader` (на каждый запрос строка INFO `recognized (…)`: тип, показание,
уверенность, readable, issues, пояснение и есть ли серийник — без изображения и без самого номера).
Порт 8000 открыт только на 127.0.0.1 хоста.

## Запуск отдельно (из этой папки)

```bash
cp .env.example .env        # заполнить YC_API_KEY и YC_FOLDER_ID
docker compose up --build
```

Без Docker:

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn meter_reader.api:app --port 8000
```

## API

`POST /recognize`: multipart-форма с полем `image` и необязательными подсказками:
`meter_type` (`cold_water` | `hot_water` | `electricity` | `gas` | `heat`) и `tariffs` (`1`..`3`).
С подсказкой промпт собирается под тип (`build_prompt` в `meter_reader/prompts.py`: блок «Known meter type» и
правила чтения этого типа); без неё или с неизвестным значением используется прежний универсальный промпт.
В блоке типа есть строка о том, как выглядит заводской номер этого типа и чем он не является (год, ГОСТ, Qn,
номер пломбы). `serial_number` приходит без «№»/«No.»/«S/N» и пробелов по краям.

```bash
curl -F image=@meter.jpg -F meter_type=hot_water http://localhost:8000/recognize
```

```json
{
  "meter_type": "hot_water",
  "reading": 595.825,
  "reading_text": "00595.825",
  "integer_digits": "00595",
  "fraction_digits": "825",
  "unit": "m3",
  "tariff": null,
  "brand": "Бетар",
  "model": "СГВ-15",
  "serial_number": "123456",
  "confidence": 0.95,
  "type_evidence": "red ring and 'СГВ' marking",
  "readable": true,
  "issues": [],
  "issue_note": null
}
```

Поля про качество фото (сервис никогда не отдаёт «пустой успех»):
- `readable` — основное показание уверенно прочитано. Нет цифр → всегда `false`.
- `issues` — коды из фиксированного набора (контракт с ботом): `no_meter`, `wrong_type` (тип не совпал с
  переданным `meter_type`), `digits_not_visible`, `blurry`, `glare`, `too_dark`, `angle`, `partially_covered`,
  `multiple_meters`, `serial_not_visible` (не мешает `readable=true`), `display_off`, `other`.
  Неизвестные коды модели превращаются в `other`, без дублей. Нет цифр и нет причины → `digits_not_visible`.
- `issue_note` — пояснение на русском для человека (≤120 символов); если модель его не дала, а показание
  не прочитано или тип не тот, подставляется типовая фраза.
- Промпт требует честности: бледное/зашумлённое табло и хоть одна неуверенная цифра → `confidence` ≤ 0.5 и
  `blurry`/`digits_not_visible`, недостающие разряды не дописывать; у LCD света — сверить число разрядов с
  типичным (5–6 целых) и написать в `issue_note`, сколько видно; нечитаемый номер/штрихкод → `serial_not_visible`.

Из консоли (нужны `curl` и `python3`):

```bash
./recognize.sh meter.jpg [ещё.jpg ...]
# другой адрес сервиса:
METER_API=http://host:8000 ./recognize.sh meter.jpg
```

`meter_type`: `hot_water` | `cold_water` | `electricity` | `gas` | `heat` | `unknown`.
`unit`: `m3` | `kWh` | `Gcal` | `MWh` | `GJ` (если модель не указала, берётся типовая для счётчика).
`tariff`: `T1` | `T2` | `T3`, `total` (сумма) или `null`.
Ошибки: `400` — файл не является изображением, `502` — ошибка Yandex Cloud или некорректный ответ модели.
Документация OpenAPI: `http://localhost:8000/docs`. Проверка работоспособности: `GET /health`.

## Как бот использует ответ

Бот и мини-приложение шлют `POST /recognize` с полем `image` и подсказками `meter_type`, `tariffs`
(тип пользователь уже выбрал). Клиент ждёт 20 с.
Если поменяете формат ответа, поправьте `HttpRecognizer._parse` и `tests/test_recognizer.py` в корне.

- Показание берётся из `reading_text` (строка, без ошибок float), иначе из `reading`. Нет показания → «не получилось
  разобрать», пользователю предлагают переснять или ввести вручную. Любой не-200 ответ — то же самое.
- `serial_number` сверяется с номером сохранённого счётчика (и сохраняется у нового). Номер обязателен: если его нет
  ни у счётчика, ни на фото, бот просит переснять или ввести номер вручную.
- `tariff` (`T1`/`T2`/`T3`) у многотарифного электросчётчика определяет, в какое поле попадёт значение; остальные
  тарифы пользователь вводит вручную, распознанный показан подсказкой.
- `confidence` сервиса ниже 0.6 → «не получилось распознать»; 0.6–0.8 → показание с предупреждением «Мы не уверены
  в цифрах». `blurry`/`digits_not_visible`/`partially_covered` при целой части короче типичной (вода, газ, свет —
  меньше 5 разрядов) → тоже «не получилось распознать». Остальные `issues` при `readable=true` показываются на
  экране проверки конкретно («Фото нечёткое — сверьте каждую цифру с табло»). Бот сам просит «Проверьте цифры
  внимательно», если `meter_type` не совпал с выбранным счётчиком, если цифр больше, чем на табло такого типа
  (вода и газ 5 + 3, свет 6 + 2), или если это не водомер.
- Показание показывается так, как прочитано (`integer_digits`/`fraction_digits`, `reading_text`): «2168», а не
  «2168,00» — дробную часть, которую модель не прочитала, бот не дорисовывает.
- `brand` и `model` сохраняются в `readings.recognized_json` вместе с показанием (служебные данные: пользователю
  не показываются и с серийным номером не смешиваются). `unit` и `type_evidence` пока не используются.

## Тесты без сети

```bash
pip install -r requirements.txt pytest && python -m pytest -q
```

## Как устроено

1. Изображение поворачивается по EXIF, уменьшается до 1600 px и кодируется в JPEG.
2. Модель получает промпт (`meter_reader/prompts.py`) и возвращает JSON. Показание она выдаёт **по барабанам**: для каждого барабана указаны цифра и цвет (чёрный — целые м³, красный — дробная часть). Если просить сразу готовое число, модель часто теряет последнюю цифру или ставит запятую не туда: при таком подходе точность была 47% против 77%.
3. Постобработка (`meter_reader/recognizer.py`): у водомера с 8 барабанами разбиение принудительно делается 5 + 3. Модель иногда ошибается с цветом крайнего барабана, а у российских водомеров почти всегда 5 чёрных и 3 красных. Если JSON битый, делается повторный запрос.

«Размышления» модели (`YC_ENABLE_THINKING=true`) выключены. На тесте они работали примерно в 10 раз медленнее (~28 с на фото), в 42% случаев исчерпывали лимит токенов, а точность заметно не росла.

## Качество

Датасет [Yandex.Toloka Water Meters](https://www.kaggle.com/datasets/tapakah68/yandextoloka-water-meters-dataset): 1244 фото водомеров, горячих и холодных.

```bash
python scripts/eval_water.py --data data/WaterMeters --limit 400 --seed 7
```

| Выборка | Точное показание | Верные целые м³ | Время на фото |
|---|---|---|---|
| 100 фото (на них подбирался промпт) | 81% | 94% | ~2.5 с |
| 373 отдельных фото | **74%** | **91%** | ~2.7 с |

Цифры измерены до добавления типовых промптов и полей `readable`/`issues`; после этих изменений eval
стоит перезапустить (скрипт работает без подсказки типа, то есть на универсальном промпте).

Если целая часть верна, а дробная нет, ошибка в 80% случаев не больше 10 литров. Обычно это барабан, который прокручивается между цифрами (такие случаи спорны и в самой разметке).

Известные проблемы:
- `confidence` от модели почти всегда 0.95, поэтому полагаться на него нельзя;
- названия брендов не нормализованы (`БЕТАР` / `BETAP`, `НОРМА` / `Норма`);
- тип «горячая/холодная» в датасете не размечен, поэтому его точность не измерялась.
