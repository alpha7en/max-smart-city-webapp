# live-scenario: пройди сценарий в MAX

Цель: найти расхождения живого бота с ожиданиями из `docs/LIVE_CHECKLIST.md`, а не «доказать, что работает».
Можно писать только в чат владельца с ботом (`https://web.max.ru/420790200`, user_id 5273381). Другим людям
ничего не отправлять, URL мини-приложения и настройки бота в MAX не менять, токен не печатать.

## 1. Подготовка
1. `.venv/bin/python -m tools.live_smoke`: без FAIL (если есть FAIL, сначала скилл `live-smoke`).
2. Бот запущен в одном экземпляре. Если он крутится и на сервере, спроси владельца, где проверяем: там или локально
   (второй экземпляр остановить).
   ```bash
   docker compose up -d --build && curl -s localhost:8080/api/health
   # без docker: .venv/bin/uvicorn app.main:app --env-file .env --port 8080
   ```
3. В отдельном фоне держи логи: `docker compose logs -f --since 1m app`. Состояние смотри в БД:
   `sqlite3 data/bot.db "select state, data from sessions s join users u on u.id=s.user_id where u.max_user_id=5273381"`
   (если sqlite3 нет: `.venv/bin/python -c "import sqlite3; ..."`).
4. Чистый старт: Профиль → «Удалить мои данные». Если этого пункта ещё нет, спроси владельца и удали `data/bot.db` при остановленном боте.
5. Для шага с фото нужна картинка счётчика. Попроси её у владельца или возьми любую: демо-распознавание работает на любом фото.
   Проверяешь реальное распознавание: в `.env` должен быть включён `meter-reader` (README, «Реальное распознавание
   показаний»), `curl -s localhost:8000/health` отвечает, логи держи и по нему: `docker compose logs -f meter-reader`.
   Нужно настоящее фото водомера (из датасета: `УСЛОВИЯ/сырые файлы…/data/WaterMeters/images`, верное значение в имени файла).

## 2. Как управлять браузером (выбери первое доступное)
**A. Claude in Chrome** (расширение в браузере владельца, инструменты вида `mcp__claude-in-chrome__*`). Владелец уже
залогинен в MAX. Открой `https://web.max.ru/420790200`, читай страницу и делай скриншоты, вводи текст в поле
сообщения, нажимай кнопки по тексту. Если загрузить файл не получается, попроси владельца прислать фото самому.

**B. Playwright с отдельным профилем.** Основной профиль Chrome занят, пока браузер открыт, поэтому профиль нужен свой.
```bash
.venv/bin/pip install playwright && .venv/bin/python -m playwright install chromium
```
Сценарий пиши во временный `data/pw_max.py` (в git не попадает). Используй
`launch_persistent_context("data/pw-profile", headless=False)`. При первом запуске владелец входит в MAX сам
(QR или SMS), дальше сессия сохраняется. Локаторы бери по тексту и роли (`get_by_text`, `get_by_role("button")`),
фото отправляй через `set_input_files`, скриншоты клади в `data/shots/NN.png`. Вёрстка web.max.ru не документирована:
сначала сделай снимок страницы, потом подбирай локаторы.

**C. Без автоматизации.** Давай владельцу по одному шагу («напишите боту: привет»). Сам в это время читай
`docker compose logs --since 2m app` и БД, потом спроси, что он видит (или попроси скриншот). Сверяй и записывай.

## 3. Прогон
Иди по разделам 1–5 чек-листа по порядку. Для каждого шага:
1. Выполни действие и подожди 2–5 с (дольше для фото: там скачивание и распознавание).
2. Посмотри, что пришло: тексты, кнопки (подпись целиком? нет `**`, тегов, сырых URL?), лог (`trace=`, `MAX API`),
   state в БД, файлы в `data/photos/`.
3. Сравни с колонкой «Должно произойти». Отличие по смыслу, тупик, молчание, 4xx в логе, трассировка = BUG.
   Если текст отличается, а смысл тот же, это NOTE.
4. Шаги [НЕ ПРОВЕРЕНО] закрой явно:
   - контакт и фото: запусти `tools.live_smoke --listen` (бот остановлен) или посмотри логи и БД;
   - initData и start_param: в DevTools выбери контекст фрейма мини-приложения и выполни
     `WebApp.initData.length`, `WebApp.initDataUnsafe.start_param`. В Playwright:
     `page.frames` → `frame.evaluate("window.WebApp && WebApp.initData.length")`. Саму строку initData
     не публикуй: это подпись. Проверяй её через `tools.live_smoke --check-init-data`.
   - мини-приложение ходит в бэкенд по `MINIAPP_API_BASE`, то есть на сервер. Без деплоя раздел 4 проверяется частично.
5. На BUG не останавливайся: запиши и иди дальше, если сценарий позволяет. Если застрял, начни с «меню».

## 4. Отчёт `data/live_report.md` (data/ в .gitignore, не коммитить)
```markdown
# Живой прогон <дата>, коммит <git rev-parse --short HEAD>, способ: A/B/C
| # | Шаг | Итог | Что пришло | Лог/trace | Гипотеза → файл |
Итого: BUG n, NOTE n. Не проверено: …
## Предлагаемые фиксы
1. <симптом> → <причина> → <файл:функция> → <правка>, тест: <какой>
```
После отчёта предложи владельцу фиксы. Маленькие очевидные фиксы (текст, подпись кнопки, формат) делай сразу
по схеме скилла `fix-from-logs`: воспроизводящий тест → правка → `python -m pytest -q` → `docker compose up -d --build`
→ повторить шаг вживую. Крупные только после согласия владельца. Подтверждённые факты о MAX перенеси в CLAUDE.md,
пометки [НЕ ПРОВЕРЕНО] в чек-листе обнови.
