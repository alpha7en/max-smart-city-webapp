Бот сам забирает обновления из MAX (long polling), входящих подключений к нему нет. Мини-приложение
и его API отдаёт nginx с одного домена. Синим выделены наши сервисы; во внешние сервисы ходят только они.

## Компоненты

| Компонент | Где | Что делает |
|---|---|---|
| `app` | контейнер `app`, порт 8080 | один процесс FastAPI (`app/main.py`): бот (long polling MAX), планировщик, API мини-приложения и его статика |
| `recognizer` | контейнер `recognizer`, порт 8000 (на хост — только `127.0.0.1`) | `services/recognizer`: `POST /recognize`, фото → мультимодальная модель Qwen в Yandex Cloud AI Studio → показание, тип, заводской номер |
| SQLite | `DATA_DIR/bot.db` (в Docker — том `./data`) | все данные; режим WAL |
| Мини-приложение | `app/web/static/` | `index.html`, `app.js`, `styles.css` без сборки; на проде их отдаёт nginx с того же домена, что и API |

В `lifespan` приложение открывает БД (с миграциями), создаёт клиентов MAX, ФГИС и адресов, запускает две
фоновые задачи — планировщик и poller (poller только при заданном `BOT_TOKEN`) — и закрывает всё при остановке.

Правила слоёв:
- `app/domain/` — чистые функции без ввода-вывода. Исключение — `dashboard.py`: берёт готовые тексты из
  `app/bot/texts/`, а `load_dashboard()` читает строки через `repo`.
- `app/integrations/` — единственное место, где есть внешний HTTP.
- `app/repo.py` — весь SQL. Транзакция: `async with repo.tx():`, вложенные вызовы допустимы.
- `app/bot/texts/` — все тексты бота и API; сами строки лежат в `texts/yaml/*.yaml`.
- Общая логика бота и API вынесена в сервисы: `app/readings.py` (подача), `app/sharing.py` (общий доступ),
  `app/verification.py` (поверка по ФГИС), `app/domain/dashboard.py` (дашборд).

## Путь сообщения MAX от пользователя

1. `bot/poller.py`: `GET /updates?marker&timeout=25`. `marker` хранится в `kv.poll_marker`, поэтому после
   рестарта апдейты не теряются и не повторяются. На каждый апдейт — отдельная задача: опрос не ждёт обработки.
   Сбой опроса — повтор через 5 → 60 с.
2. `bot/events.py`: апдейт → `Event` (`start`, `text`, `photo`, `contact`, `location`, `callback`, `other`).
   Сообщения не из личного диалога и от ботов отбрасываются. Кто нажал кнопку — `callback.user`
   (в `message.sender` лежит сам бот).
3. `bot/router.py`, `Router.handle`: дубли апдейтов отбрасываются (последние 2000 id), события одного
   пользователя обрабатываются строго по очереди (лок на пользователя). Если пользователь жмёт кнопку, пока
   обрабатывается прошлое событие, на нажатие отвечают сразу, чтобы кнопка не «крутилась».
4. Загружаются пользователь (`users`, создаётся при первом событии) и сессия (`sessions`). Применяются общие
   правила для неожиданного ввода ([bot.md](bot.md#правила-роутера)), затем вызывается обработчик состояния из `bot/flows/`.
5. Обработчик работает с `ctx` (`bot/ctx.py`): `ctx.reply()` на нажатие кнопки заменяет сообщение с кнопкой
   (`POST /answers`), иначе шлёт новое; `ctx.note()` добавляет строку в начало следующего сообщения.
   На каждый callback бот отвечает MAX, даже если обработчик этого не сделал.
6. Сессия сохраняется только после успешной обработки. Исключение в обработчике → в логе
   `handler failed trace=<8 hex>`, пользователю «Что-то пошло не так…» с кнопками «Повторить» / «В меню»,
   состояние остаётся прежним.

Сценарии регистрируют обработчики декораторами (`@on_state`, `@on_repeat`, `@on_global`, `@on_command`,
`@on_hook`); `router.py` при этом не меняется. Сценарии вызывают друг друга только через точки входа
(`call_hook`, список — `HOOK_NAMES`).

**Кнопки.** Payload — `flow|action|arg` (не длиннее 64 байт). `flow` — `flow_id` текущей сессии (6 hex-символов)
или `g` для глобальных кнопок (меню, уведомления, карточки). Новый сценарий получает новый `flow_id`, поэтому
кнопка из старого сообщения распознаётся как устаревшая. Все кнопки строятся в `bot/keyboards.py`, который
проверяет лимиты MAX (30 рядов, 7 кнопок в ряду, не больше 3 link/open_app/request_* в ряду, публичный URL
у `link`, username бота у `open_app`) и падает на нарушении, а не обрезает молча.

## Мини-приложение

Мини-приложение ходит в `/api/*` с заголовком `X-Max-Init-Data` ([api.md](api.md)) и использует те же
`repo`, `readings.submit_reading()`, `sharing` и дашборд, что и бот. После подачи из мини-приложения бот пишет
подтверждение в чат и в фоне проверяет поверку по ФГИС. Профиль и адреса мини-приложение само не меняет:
кнопки открывают чат диплинком `max.ru/<бот>?start=<payload>`, и бот запускает нужный сценарий
([bot.md](bot.md#диплинки)).

## Фоновые задачи

`app/scheduler.py`, тик раз в минуту:
- каждый тик — удаление просроченных временных фото (файл и строка `photos`);
- раз в 10 тиков с 9:00 до 20:59 по `TZ` — уведомления: каждому зарегистрированному пользователю не больше
  одного за проход, каждое уведомление — один раз (таблица `notifications`, ключ содержит этап);
- раз в 60 тиков — обновление поверки по ФГИС. Реально выполняется раз в сутки (`kv.arshin_refresh_day`),
  только в `ARSHIN_MODE=live`, не больше 10 счётчиков; при недоступности ФГИС проход останавливается.

Просроченные сессии подачи и профиля планировщик не трогает: их сбрасывает роутер при следующем событии.

## Данные

SQLite, одно соединение `aiosqlite` на процесс, доступ сериализует реентерабельный лок `Repo`.
Схема версии 1 — `app/schema.sql`, дальше миграции `db.MIGRATIONS` по `PRAGMA user_version`; они применяются
при старте. Новая таблица или поле — только новой миграцией.

| Таблица | Что хранит |
|---|---|
| `users` | MAX `user_id`, `chat_id`, ФИО, телефон и получен ли он из MAX, дата регистрации. `max_user_id < 0` — демо-люди `/demo_profile` без аккаунта MAX |
| `addresses` | нормализованный адрес: `norm_key` (уникальный ключ), статус проверки (`verified_flat`, `verified_house`, `unverified`), источник (`dadata`, `local`), поля ФИАС |
| `user_addresses` | связь человек ↔ адрес: роль `owner`/`tenant`, доступ `granted`/`pending`/`denied`, короткая подпись `label` для кнопок, кто и когда открыл доступ (`granted_by`, `granted_at`) |
| `meters` | счётчик адреса: тип, тарифы (1–3, больше одного — только у электричества), заводской номер (`serial` для показа, `serial_norm` для сравнения, уникален в пределах адреса), срок поверки и его источник (`user`, `model`, `arshin`), запись ФГИС, `active` (удаление мягкое) |
| `readings` | показание за период `YYYY-MM`: `t1..t3` в тысячных долях единицы, источник (`photo`, `photo_edited`, `manual`, `miniapp`), статус (`accepted`, `flagged` — большой прирост, `replaced` — заменено), что вернул распознаватель. Действующее показание одно на счётчик и месяц |
| `sessions` | состояние диалога, данные сценария (JSON), `flow_id`, срок жизни |
| `photos` | временные фото: путь к файлу и срок жизни |
| `bills` | демо-счета: адрес, период, сумма в копейках, срок оплаты |
| `notifications` | что уже отправлено: `(user_id, kind, dedup_key)` уникальны |
| `invites`, `invite_addresses` | одноразовые ссылки «Поделиться доступом» и их адреса |
| `arshin_cache` | ответы ФГИС по «тип:номер» |
| `kv` | маркер long polling и служебные отметки |

Показания — всегда целые числа в тысячных долях (`123,456 м³` → `123456`), без float. Время в БД — UTC
в формате `YYYY-MM-DD HH:MM:SS`; «сейчас» берётся из `app.clock` (в тестах подменяется).

«Удалить мои данные» удаляет пользователя, его связи с адресами, сессию, фото, историю уведомлений и ссылки.
Счётчики и показания остаются за адресом без привязки к человеку. Если удаляется собственник, адрес переходит
первому, кому он открыл доступ.

## Интеграции

### MAX Bot API — `integrations/max_api.py`

Тонкий клиент на httpx. Заголовок `Authorization: <token>` без `Bearer`. TLS проверяется всегда: certifi плюс
сертификаты Минцифры из `certs/`. Повторы 1 → 2 → 4 с при сетевой ошибке, 429, 5xx и `attachment.not.ready`
(кроме long polling — там повторяет poller). Фото скачивается по URL из вложения без токена: не больше 10 МБ,
только `image/*` или `application/octet-stream`.

### Распознавание — `integrations/recognizer.py`

- `HttpRecognizer` (задан `RECOGNIZER_URL`): `POST` multipart `image` + подсказки `meter_type`, `tariffs`.
  Ответ сервиса переводится в `Recognition` только в `HttpRecognizer._parse` — это единственная граница с сервисом.
- `StubRecognizer` (демо): прошлое показание плюс правдоподобный прирост, детерминированно от фото. Подпись к фото
  «ошибка» (можно с кодом, например «ошибка glare») показывает экран неудачи.

Уверенность считает клиент, а не сервис (у сервиса она почти всегда 0.95):
- «не распознали» — `readable=false`, нет значения, сбой сервиса, `confidence` сервиса ниже 0.6,
  или размыто/цифры не видны при недоборе целых цифр;
- прочитали с оговорками — предупреждения на экране проверки: коды `issues` сервиса, `low_confidence`
  (сервис ниже 0.8), `few_digits`. «Проверьте цифры» — если тип не совпал, цифр больше, чем на табло
  такого типа, или это не водомер (на данных проверены только водомеры).

Показание показывается как прочитано (`2168`, без дописанных нулей). Производитель и модель с шильдика пишутся
только в `readings.recognized_json` и помогают выбрать запись ФГИС. Таймаут клиента 20 с, общий в боте 25 с.

### Адреса — `integrations/address_service.py`, `domain/addresses.py`

С `DADATA_API_KEY` — подсказки DaData (только дома с ФИАС-id), при сбое или без ключа — локальный разбор
строки (город, улица, дом, корпус/строение/литера, квартира; статус `unverified`). Одинаковые адреса
склеиваются по `norm_key`: `h:<house_fias_id>|f:<кв>` или по нормализованному тексту. Короткие подписи для
кнопок (`Арбат 47к1, кв 32`, не длиннее 24 символов) пересчитываются для всего набора адресов пользователя так,
чтобы они различались. В тексте сообщений всегда полный адрес.

### ФГИС «Аршин» — `integrations/arshin.py`, `domain/verification.py`, `app/verification.py`

Официальный публичный API `GET /eapi/vri` Росстандарта, без ключа; доступен только с российских IP.
- Лимит 2 запроса в секунду: между любыми запросами процесса пауза не меньше 0,6 с.
- Поиск идёт только за текущий год, если не задать начало: бот передаёт
  `verification_date_start = сегодня − межповерочный интервал − 1 год`, на 400/408 перебирает годы.
- Номер пробуется в нескольких написаниях (как есть, без разделителей, без ведущих нулей, без префикса года у воды).
- На проверку — не больше 4 запросов; один повтор на 429/5xx/таймаут; после 3 сбоев подряд — 10 минут без запросов.
- Кэш в `arshin_cache`: найдено — 30 дней, не найдено — 3 дня.
- Заводской номер уникален только внутри типа СИ, поэтому записи фильтруются по наименованию типа, группируются
  по номеру типа СИ, в группе берётся последняя поверка. Одна подходящая группа (или единственная, где совпали
  марка/модель с фото) — дата записывается сама; несколько — бот спрашивает «Это ваш счётчик?».
- После подачи бот ждёт ответ не дольше 6 с, дальше проверка доделывается в фоне. Дату из паспорта
  (`verification_source='user'`) ФГИС не перезаписывает.
- `ARSHIN_FALLBACK_IPS`: если DNS в контейнере не резолвит `fgis.gost.ru`, соединение идёт на известные IP;
  TLS и SNI при этом проверяются по имени хоста.
- `ARSHIN_MODE=fixtures` — демо-записи из `integrations/arshin_demo.json` без сети (номер на `0` — записи нет,
  на `9` — два прибора с одним номером); в сообщениях пометка «демо-данные».

## Безопасность

- initData мини-приложения проверяется по HMAC-SHA256 (ключ — `HMAC("WebAppData", BOT_TOKEN)`) и сроку
  `INIT_DATA_TTL`. Без валидной подписи API отвечает 401. `X-Dev-User` принимается только при `DEV_AUTH=true`.
- CORS выключен, пока не задан `MINIAPP_ORIGINS`. Мини-приложение принимает параметр `?api=` только
  для localhost, чтобы initData не ушёл на чужой хост.
- TLS не отключается нигде; в `certs/` только публичные сертификаты.
- Секреты — только в `.env` (в `.gitignore`); токен не пишется в логи. `tests/test_security.py` ищет ключи
  и `verify=False` в отслеживаемых файлах.
- Контейнер `app` работает от непривилегированного пользователя. Временные фото — файлы с правами 0600,
  удаляются после подачи, отмены или по сроку (30 минут; фото, присланное до регистрации, — 24 часа).
  Фото из мини-приложения удаляется сразу после распознавания. На время распознавания фото уходит в Yandex Cloud.
- Пользовательский ввод экранируется перед разметкой (`texts/fmt.esc`).

## Как расширять

- **Новый тип счётчика:** `MeterType` и `SPECS` в `domain/meters.py` (подпись, единица, разрядность, порог
  прироста), миграция для `CHECK` на `meters.type`, пример ввода в `texts/yaml/submission.yaml` (`EXAMPLES`,
  `SERIAL_EXAMPLES`, `SERIAL_TYPICAL`), кнопка в `flows/submission.TYPE_ROWS`, параметры демо-заглушки
  в `integrations/recognizer.py`, формат номера в `domain/serials.DIGITS`.
- **Распознавание:** сервис меняется независимо; при смене формата ответа правится только `HttpRecognizer._parse`
  и `tests/test_recognizer.py`. Проверенный на данных тип добавляется в `_VALIDATED`.
- **Передача в УК:** отдельный клиент в `app/integrations/`, вызов после успешного `readings.submit_reading()`,
  затем убрать пометку «передача смоделирована».
- **Окно подачи по адресу:** хранить график у адреса и передавать его в `domain/meters.submission_window()`
  вместо общих `SUBMIT_DAY_FROM/TO`.
- **Webhook вместо long polling:** маршрут в `web/` принимает апдейт от MAX и делает то же, что
  `Poller.poll_once()` для каждого апдейта: `parse_update()` → `router.handle()`. Подписка — `POST /subscriptions`
  на HTTPS-адрес за nginx; при активной подписке `GET /updates` не работает, поэтому poller в `main.py` не запускается.
