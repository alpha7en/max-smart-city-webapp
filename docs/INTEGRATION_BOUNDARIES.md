# Спецификация интеграционных границ и MVP-заглушек платформы «MAX Умный Дом ЖКХ»

**Версия документа**: 1.0.0  
**Дата утверждения**: 24 сентября 2026 г.  
**Статус**: Утвержден / Архитектурный стандарт (Milestone 3)  
**Область действия**: Архитектура микросервисов, REST API, MAX Bot SDK, доменные службы `app/services/`

## 1. Архитектурная философия: Инвариантное ядро против внешних границ

Платформа «MAX Умный Дом ЖКХ» разработана в соответствии с методологией изолированных границ (Clean Architecture / Hexagonal Architecture). Архитектурный контур системы строго разделен на две фундаментальные категории:

```
+-----------------------------------------------------------------------------------+
|                        ПРОИЗВОДСТВЕННОЕ ЯДРО (CORE PLATFORM)                      |
|                                                                                   |
|  [FastAPI REST API] ──► [FSM Диспетчер Bot SDK] ──► [Бизнес-правила & Защита]     |
|         │                        │                               │                |
|         ▼                        ▼                               ▼                |
|  [SQLite WAL DB]         [MAX WebApp Bridge]            [Фильтр x1000 / Монотон]  |
+------------------------------------------┬----------------------------------------+
                                           │ Точки изоляции (PASS / STUB)
                                           ▼
+-----------------------------------------------------------------------------------+
|                     ВНЕШНИЕ ИНТЕГРАЦИОННЫЕ АДАПТЕРЫ (MVP STUBS)                    |
|                                                                                   |
|  [ГИС ЖКХ]      [ФГИС «АРШИН»]      [Банк СБП 40821]      [1С:ЖКХ]    [AI Vision]  |
|  (209-ФЗ SOAP)    (102-ФЗ REST)     (ГОСТ / 103-ФЗ)      (63-ФЗ АРМ)  (YOLOv8 OCR) |
+-----------------------------------------------------------------------------------+
```

### 1.1. Инвариантное ядро платформы (Production Code)
Все компоненты ядра реализуют настоящую логику, поддерживают персистентное состояние и исполняются без заглушек:
1. **HTTP/REST транспорт**: FastAPI 0.115+, валидация Pydantic v2, строгая типизация параметров, аутентификация через проверку HMAC-SHA256 подписи `initData` мессенджера MAX.
2. **Персистентность данных**: SQLite 3 с принудительным режимом журнала WAL (`PRAGMA journal_mode=WAL;`), сериализацией транзакций и Docker Volume (`./data:/app/data`).
3. **Бизнес-правила приборов учета**:
   - Алгоритм защиты от ошибки в 1000 раз: автоматическое отсечение красных барабанов (литровых долей) для счетчиков холодной/горячей воды и газа;
   - Контроль монотонности показаний: запрет ввода значений ниже предыдущего показания;
   - Эвристика аномального потребления: выявление скрытых утечек при расходе воды > 25 м³/мес или электроэнергии > 1000 кВт*ч/мес.
4. **Финансовый парсер ГОСТ Р 56042-2014**: расчет контрольного ключа расчетного счета по алгоритму Банка России (модуль 10 с весовыми коэффициентами 7, 1, 3).
5. **Мобильное рабочее место обходчика**: генерация неизменяемого криптографического слепка SHA-256 по полям акта, фиксация координат ГЛОНАСС/GPS и временной метки ISO-8601.
6. **Асинхронный диспетчер MAX Bot SDK**: неблокирующая обработка Long Polling событий, машина конечных состояний диалогов (FSM UserState), контекстное хранилище.

### 1.2. Внешние интеграционные адаптеры (MVP Stubs / PASS)
Для целей хакатона, демонстрации жюри и автономного CI/CD тестирования сервисы, требующие закрытых межведомственных каналов СМЭВ 3.0, аппаратных СКЗИ (КриптоПро CSP по ГОСТ), промышленных банковских шлюзов эквайринга или серверных GPU-кластеров, изолированы в адаптерах-заглушках.
Каждая заглушка:
- Реализует 100% валидацию реального входного контракта данных;
- Имитирует детерминированное поведение целевой государственной или банковской системы;
- Маркируется стандартизированным комментарием `# MVP STUB: <NAME> -> PASS` и структурированным логом `logger.info("MVP STUB: <NAME> -> PASS (...)")`;
- Имеет четко определенную точку остановки (`PASS / STUB`), где прекращается внутренняя обработка и возвращается стандартизированный ответ.

## 3. Стандартизированный протокол маркировки кода и телеметрии

В кодовой базе платформы принят строгий формат маркировки точек интеграционного перехода:

### 3.1. Комментарий в коде
Перед вызовом или возвратом из эмулируемого интерфейса размещается комментарий:
```python
# MVP STUB: <INTEGRATION_KEY> -> PASS
```
Где `<INTEGRATION_KEY>` принимает одно из 5 фиксированных значений:
1. `GIS_ZHKH`
2. `FGIS_ARSHIN`
3. `SBP_BANK`
4. `1C_ZHKH`
5. `OCR_MODEL`

### 3.2. Системное логирование
В месте срабатывания заглушки вызывается логирование уровня `INFO` с ключевыми параметрами операции:
```python
logger.info("MVP STUB: <INTEGRATION_KEY> -> PASS (<key_params>)")
```

## 4. Детальные спецификации 5 интеграционных границ

### 4.1. ГИС ЖКХ (Государственная информационная система жилищно-коммунального хозяйства)

- **Законодательное обоснование**: 
  Федеральный закон от 21.07.2014 № 209-ФЗ «О государственной информационной системе жилищно-коммунального хозяйства». Приказ Минкомсвязи РФ № 74, Минстроя РФ № 114/пр от 29.02.2016.
- **Целевой промышленный протокол**:
  - Транспорт: SOAP 1.2 over HTTPS (ГОСТ TLS).
  - Спецификация WSDL: Сервис `hcs-device-meterings`, операция `importMeteringDeviceValuesRequest`.
  - Аутентификация: Квалифицированный сертификат электронной подписи (ГОСТ Р 34.10-2012) организации-поставщика данных.
  - Идентификация абонента: 10-значный Единый Лицевой Счет (ЕЛС, формат `10XXXXXXXX`), Номер ПУ (заводской номер).
- **Контракт входных данных (Input Data Contract)**:
  - `els`: `str` — 10 символов, ЕЛС абонента (например, `"1004567890"`).
  - `meter_id`: `str` — внутренний идентификатор прибора (например, `"meter-khvs-1"`).
  - `reading_value`: `float` — передаваемое показание в единицах учета (м³, кВт*ч, Гкал).
  - `submission_channel`: `str` — канал передачи (`"chat_photo_drop"`, `"miniapp_manual"`, `"inspector_arm"`).
- **Контракт выходных данных (Output Data Contract)**:
  - `is_valid`: `bool` — подтверждение успешности приема показаний (`True`).
  - `current_value`: `float` — зафиксированное значение с отсеченными красными барабанами.
  - `previous_value`: `float` — предыдущее показание прибора.
  - `consumption`: `float` — рассчитанный расход за расчетный период.
  - `message`: `str` — юридическое подтверждение: `"Показания успешно приняты и зафиксированы в ГИС ЖКХ."`.
- **Логика MVP-заглушки (`app/services/meter_service.py`)**:
  1. Выполняется локальная валидация монотонности (`current >= previous`). При попытке сдать показания меньше предыдущих формируется отказ без передачи во внешнюю систему.
  2. Выполняется проверка фильтрации красных роликов: если пользователь или камера передали показания вместе с литровыми барабанами (например, `145789`), значение автоматически преобразуется к `145.0` м³, предотвращая переплату в 1000 раз.
  3. Выполняется проверка на всплеск потребления (> 25 м³ для воды, > 1000 кВт*ч для света). При аномалии возвращается предупреждение о скрытой утечке.
  4. Запись атомарно сохраняется в таблицу `meter_readings` базы данных SQLite (`smart_city.db`).
- **Точка остановки (PASS / STUB)**:
  После сохранения в локальную БД и формирования результата выводится лог:
  ```python
  # MVP STUB: GIS_ZHKH -> PASS
  logger.info("MVP STUB: GIS_ZHKH -> PASS (meter_id=%s, value=%.3f, channel=%s)", req.meter_id, filtered_val, req.submission_channel)
  ```
  Сетевой SOAP-запрос к контуру `hcs.gosuslugi.ru` не инициируется, эмулируется гарантированный HTTP 200 OK ответ шлюза ГИС ЖКХ.

### 4.2. ФГИС «АРШИН» (Государственный реестр Росстандарта)

- **Законодательное обоснование**:
  Федеральный закон от 26.06.2008 № 102-ФЗ «Об обеспечении единства измерений» (в редакции 496-ФЗ). С 24 сентября 2020 года единственным юридически значимым фактом поверки является электронная запись в реестре Росстандарта (бумажные свидетельства носят исключительно информационный характер).
- **Целевой промышленный протокол**:
  - Транспорт: REST JSON API.
  - Базовый URL: `https://fgis.gost.ru/fundmetrology/eapi/vri?search={serial_number}`.
  - Аутентификация: Открытый публичный реестр с лимитом запросов (Rate Limit 60 req/min).
  - Формат ответа: JSON массив объектов поверок с полями `vri_id`, `org_title`, `verification_date`, `valid_date`, `applicability`.
- **Контракт входных данных (Input Data Contract)**:
  - `serial_number`: `str` — заводской номер счетчика (очищенный от пробелов, символов № и спецсимволов, например `"2809142"` или `"991201"`).
  - `meter_type`: `Optional[MeterType]` — опциональный тип ресурса для контекстной валидации.
  - `fraud_warning_on_expired`: `bool` — признак необходимости возврата предупреждения о мошенниках при истекшем сроке поверки.
- **Контракт выходных данных (Output Data Contract)**:
  - `serial_number`: `str` — очищенный заводской номер.
  - `organization_name`: `str` — наименование аккредитованной лаборатории (например, `ФБУ «РОСТЕСТ-МОСКВА»`).
  - `verification_date`: `date` — дата проведения последней официальной поверки.
  - `valid_until`: `date` — дата окончания межповерочного интервала.
  - `status`: `VerificationStatus` (`verified` | `expired` | `unregistered`).
  - `is_fraud_warning`: `bool` — флаг необходимости информирования жителя об угрозе мошенничества.
  - `shield_color`: `str` (`"green"` для легитимных, `"red"` для просроченных или поддельных).
  - `safety_message`: `str` — текст «Зеленого Щита Безопасности» с юридической защитой от спам-листовок.
  - `fgis_arshin_url`: `str` — прямая ссылка на официальный реестр ФГИС «АРШИН».
- **Логика MVP-заглушки (`app/services/arshin.py`)**:
  1. Нормализация серийного номера: удаление знака №, пробелов, приведение к верхнему регистру.
  2. Проверка на явные фальшивки (`000000`, `FAKE`, `FAKE01`): статус `unregistered`, красный щит, предупреждение о 100% мошенничестве.
  3. Поиск в эталонной БД (`ARSHIN_MOCK_DATABASE`): содержит реальные номера сертифицированных приборов (ИТЭЛМА, Бетар, Меркурий, Sayany, Elster), а также тестовый просроченный прибор `991201`.
  4. Если прибор действует: формируется «Зеленый Щит Безопасности» с точным расчетом оставшихся лет и инструкцией игнорировать спам в почтовых ящиках.
  5. Если срок истек: формируется предупреждение о начислениях по нормативу и рекомендация обратиться в официальную УК во избежание переплат мошенникам.
- **Точка остановки (PASS / STUB)**:
  ```python
  # MVP STUB: FGIS_ARSHIN -> PASS
  logger.info("MVP STUB: FGIS_ARSHIN -> PASS (serial=%s, status=%s, shield=%s)", clean_serial, status, color)
  ```
  Внешний HTTP-запрос к серверу Росстандарта блокируется во избежание сбоев при нестабильности сетевого соединения и для гарантии 100% повторяемости тестов.

### 4.3. Банк СБП и Расщепление Платежей на Спецсчета 40821

- **Законодательное обоснование**:
  - ГОСТ Р 56042-2014 «Стандарты финансовых операций. Двумерные символы штрихового кодирования для осуществления платежей физических лиц».
  - Федеральный закон от 03.06.2009 № 103-ФЗ «О деятельности платежных агентов» (обязательное использование спецсчетов 40821).
  - Федеральный закон от 03.04.2018 № 59-ФЗ «О прямых договорах с ресурсоснабжающими организациями».
  - Положение Банка России № 579-П (правила расчета контрольного ключа 20-значных банковских счетов).
- **Целевой промышленный протокол**:
  - Платежный шлюз: НСПК СБП (Система быстрых платежей C2B QR / Deeplink).
  - Банковский интерфейс: Host-to-Host (H2H) REST/MT940 шлюз уполномоченного банка (Сбербанк, ВТБ, Т-Банк) с реестровым расщеплением единого платежа.
- **Контракт входных данных (Input Data Contract)**:
  - `qr_payload`: `str` — строка квитанции стандарта ГОСТ Р 56042-2014:
    `ST00012|Name=...|PersonalAcc=40821...|BankName=...|BIC=044525225|Sum=485050|PersAcc=1004567890|Period=092026`
- **Контракт выходных данных (Output Data Contract)**:
  - `is_valid_gost`: `bool` — соответствие формата стандарту ГОСТ (`True`).
  - `recipient_name`: `str` — наименование исполнителя коммунальных услуг.
  - `payee_account`: `str` — расчетный или специальный счет 40821.
  - `is_account_checksum_valid`: `bool` — результат математической проверки контрольного ключа Банка России.
  - `total_amount_rubles`: `float` — общая сумма платежа.
  - `is_40821_split_supported`: `bool` — признак автоматического расщепления (`True`).
  - `split_details`: `List[SplitPaymentRecipient]` — массив целевых транзакций:
    1. АО «Мосводоканал» (счет `40821810500000001001`, 25% суммы);
    2. ПАО «МОЭК» (счет `40821810500000002002`, 45% суммы);
    3. АО «Мосэнергосбыт» (счет `40821810500000003003`, 15% суммы);
    4. Управляющая организация (содержание жилья, остаток суммы).
- **Логика MVP-заглушки (`app/services/gost_qr.py`)**:
  1. Синтаксический разбор заголовка `ST00011` / `ST00012` и параметров, разделенных символом `|`.
  2. Вычисление математической контрольной суммы расчетного счета: конкатенация последних цифр БИК и 20 цифр счета, умножение на периодический весовой ряд `[7, 1, 3] * 8`, остаток от деления суммы на 10 должен быть равен 0.
  3. Калькуляция пропорционального расщепления единого платежа на спецсчета 40821 в соответствии со статьей 103-ФЗ (деньги напрямую зачисляются поставщикам и защищены от блокировок и долгов УК).
- **Точка остановки (PASS / STUB)**:
  ```python
  # MVP STUB: SBP_BANK -> PASS
  logger.info("MVP STUB: SBP_BANK -> PASS (amount=%.2f, split_count=%d, account=%s)", amount_rubles, len(split_details), payee_account)
  ```
  Вызов реального межбанковского клиринга НСПК не производится; формируется готовый СБП-инвойс и модель фискального чека.

### 4.4. 1С:ЖКХ & Мобильное рабочее место обходчика УК

- **Законодательное обоснование**:
  - Федеральный закон от 06.04.2011 № 63-ФЗ «Об электронной подписи».
  - Постановление Правительства РФ от 06.05.2011 № 354 «О предоставлении коммунальных услуг собственникам и пользователям помещений в многоквартирных домах».
  - Стандартные форматы обмена «1С:Предприятие 8. Учет в управляющих компаниях ЖКХ, ТСЖ и ЖСК».
- **Целевой промышленный протокол**:
  - Транспорт: 1C OData REST API (`/odata/standard.odata/Document_АктОсмотра`) либо пакетная синхронизация EnterpriseData XML.
  - Формат документа: Электронный акт осмотра с реквизитами мастера, координатами привязки, контрольными показаниями и хешем фотоматериалов.
- **Контракт входных данных (Input Data Contract)**:
  - `meter_id`: `str` — идентификатор осматриваемого прибора учета.
  - `reading_value`: `float` — показание, снятое контролером УК.
  - `address`: `str` — адрес объекта проверки (МКД, квартира).
  - `inspector_name`: `str` — ФИО контролера службы учета.
  - `gps_coordinates`: `Optional[str]` — географические координаты места съемки.
  - `photo_base64`: `Optional[str]` — бинарный снимок шкалы счетчика в кодировке Base64.
- **Контракт выходных данных (Output Data Contract)**:
  - `act_id`: `str` — уникальный регистрационный номер акта (`ACT-ЖКХ-<timestamp>`).
  - `timestamp`: `str` — точное локальное время составления акта.
  - `gps`: `str` — подтвержденные координаты геопозиционирования с меткой ГЛОНАСС/GPS.
  - `photo_hash_sha256`: `str` — 64-символьный криптографический хеш снимка (гарантия неизменности фотодоказательства).
  - `export_1c_ready`: `bool` — готовность записи к выгрузке в 1С:ЖКХ (`True`).
  - `billing_export_status`: `str` — статус синхронизации (`"EXPORTED_TO_1C_ZHKH"`).
  - `legal_significance`: `str` — подтверждение юридической значимости по 63-ФЗ.
- **Логика MVP-заглушки (`app/services/inspector_service.py`)**:
  1. Вычисление криптографического хеша SHA-256 на основе неизменяемой строки: `act_id|meter_id|address|timestamp|reading|inspector`.
  2. Верификация GPS-метки: при отсутствии координат подставляются подтвержденные координаты инспектора.
  3. Сохранение оформленного акта в SQLite таблицу `inspector_acts`.
  4. Формирование структуры данных, готовой для прямой сериализации в JSON/XML пакет 1С:ЖКХ.
- **Точка остановки (PASS / STUB)**:

### 4.5. AI Vision & OCR Модель распознавания показаний

- **Законодательное обоснование**:
  - Технический регламент хакатона («Умный город.pdf», критерии оценки архитектуры, стр. 9–10): прямое указание на допустимость эмуляции тяжелых ML-пайплайнов с целью обеспечения сверхбыстрой сборки Docker-образа (< 5 минут) и возможности запуска на стандартных CPU без дискретных видеокарт NVIDIA.
- **Целевой промышленный протокол**:
  - Архитектура инференса: Triton Inference Server / TorchServe gRPC.
  - Модельный пайплайн: 
    1. Детектор типа прибора и прицельной рамки циферблата (YOLOv8 Nano);
    2. Выравнивание перспективы (Spatial Transformer Network / OpenCV Homography);
    3. Сегментация барабанов: отделение черных кубических роликов от красных литровых роликов;
    4. Распознавание символов (CRNN / TorchOk OCR).
- **Контракт входных данных (Input Data Contract)**:
  - `image_base64`: `Optional[str]` — изображение счетчика, переданное в чат или снятое камерой Mini-App.
  - `device_type_hint`: `Optional[MeterType]` — контекстная подсказка (ХВС, ГВС, газ, электроэнергия, отопление).
- **Контракт выходных данных (Output Data Contract)**:
  - `is_mock`: `bool` — системная метка эмуляции нейросети (`True`).
  - `mock_notice`: `str` — описание используемого пайплайна YOLOv8 + TorchOk.
  - `detected_meter_type`: `MeterType` — распознанный тип коммунального ресурса.
  - `recognized_reading`: `float` — показание целых единиц учета (м³, кВт*ч, Гкал) без дробных долей.
  - `raw_reading_with_fractions`: `float` — полное значение с учетом красных роликов (литров).
  - `recognized_serial_number`: `str` — распознанный заводской номер счетчика.
  - `confidence`: `float` — интегральная уверенность распознавания (`0.968`).
  - `red_rollers_detected`: `bool` — флаг обнаружения красных роликов.
  - `perspective_rectified`: `bool` — подтверждение успешного геометрического выравнивания кадра.
  - `bounding_boxes`: `List[BoundingBox]` — точные полигоны обнаруженных объектов (`black_digit_rollers_m3`, `red_digit_rollers_liters`, `serial_number_plate`).
- **Логика MVP-заглушки (`app/services/ai_vision.py`)**:
  1. Обработка входящего запроса: определение целевого типа счетчика по подсказке или выбор дефолтного счетчика ХВС.
  2. Генерация физически реалистичных координат ограничивающих рамок (Bounding Boxes) для отрисовки в лазерном видоискателе WebApp.
  3. Четкое разделение целочисленной части (`recognized_reading`) и литровой фракции (`raw_reading_with_fractions`), что обеспечивает эталонную работу защиты от ошибки в 1000 раз.
- **Точка остановки (PASS / STUB)**:
  ```python
  # MVP STUB: OCR_MODEL -> PASS
  logger.info("MVP STUB: OCR_MODEL -> PASS (type=%s, reading=%.3f, serial=%s, confidence=%.3f)", target_type.value, integer_reading, serial, 0.968)
  ```
  Исполнение тяжелых весов нейросети на CPU предотвращается, обеспечивая время отклика эндпоинта < 2 миллисекунд.

## 6. Дорожная карта перехода в промышленную эксплуатацию (Production Transition)

Для перевода решения из демонстрационного MVP-контура в промышленную эксплуатацию на инфраструктуре крупной УК или регионального оператора требуется:

1. **ГИС ЖКХ**:
   - Подключение защищенного канала VPN ГОСТ TLS с сертифицированным шлюзом СМЭВ 3.0;
   - Установка криптопровайдера КриптоПро CSP 5.0 на хост-системе;
   - Замена адаптера `MeterService` на вызов боевого SOAP-клиента с подписанием XML-запросов усиленной квалифицированной ЭЦП организации.
2. **ФГИС «АРШИН»**:
   - Заключение соглашения об информационном взаимодействии с ФГУП «ВНИИМС» (Росстандарт);
   - Получение API-ключа с расширенными квотами (до 10 000 запросов/час);
   - Включение Redis-кэширования результатов поверок со сроком жизни TTL = 30 дней.
3. **Банк СБП**:
   - Заключение договора эквайринга с уполномоченным банком (Сбербанк / ВТБ / Т-Банк) на обслуживание спецсчетов 40821 в соответствии со 103-ФЗ;
   - Интеграция боевых сертификатов НСПК для генерации динамических QR-кодов СБП.
4. **1С:ЖКХ**:
   - Настройка защищенного OData эндпоинта базы данных 1С:Предприятие 8;
   - Настройка регламентного фонового задания синхронизации подписанных актов обходчика с журналом документов 1С.
5. **AI Vision OCR**:
   - Развертывание контейнера Triton Inference Server на сервере с графическим ускорителем NVIDIA TensorRT;
   - Подключение обученной модели детекции циферблатов счетчиков с валидацией качества mAP50 > 98.5%.
